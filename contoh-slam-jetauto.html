EL6010 · autonomous system and robotics

A robot that maps a room while figuring out where it is

A particle filter based SLAM (Simultaneous Localization and Mapping) implementation on the JetAuto mobile robot, benchmarked head to head against ROS1 Gmapping, an industry standard framework.

Team · 4 members Platform · JetAuto + Jetson Nano Test sites · 3 locations

Overview

Imagine walking into a dark room with a flashlight

As you walk, you build a mental map of the room, where the walls are, where the door is, while also keeping track of exactly where you're standing inside it. That's exactly what this robot has to do, with no GPS and no map prepared in advance. Both things have to happen at once: the robot builds a map of its surroundings while continuously tracking its own position inside the map it's still building.

The project has two goals: run a SLAM framework (Gmapping) in real time on the Jetson Nano embedded in the robot, then measure how accurate the resulting map and position actually are against ground truth in the field.

How it works

Thousands of position guesses, sharpened step by step

The approach is called FastSLAM: the robot spreads out many particles, each one a possible guess of its position and path. Every time the robot moves and its Lidar reads the environment, those guesses get checked against the sensor data. The ones that don't fit get discarded, the ones that match get reinforced. The most convincing particles are then used to build the 2D occupancy grid, cell by cell.

Technical detail: motion model, scan matching & resampling

The formulation follows a Rao-Blackwellized Particle Filter, which splits the SLAM problem into two parts computed separately:

  • Robot trajectory is estimated with the particle filter, using an odometry motion model (a rotation, translation, rotation scheme) plus Gaussian noise.
  • Map is computed analytically (grid mapping), assuming the robot's trajectory at that step is already known.

Each particle's position is corrected through scan matching against the Lidar reading, then given an importance weight based on how well it matches. Resampling, discarding low weight particles, only runs when particle weight diversity drops below a threshold, so particles don't collapse to a single point too early. The map update itself uses an inverse sensor model with Bresenham's algorithm to mark which cells are empty and which are walls, for every Lidar ray.

The implementation was tested on two separate tracks: a custom Python implementation written from scratch, and ROS1 Gmapping as a mature, already optimized benchmark.

Experiment setup

Tested directly in campus classrooms and a corridor

The robot ran in three real locations, two classrooms (Sisken & Robotic Lab) and one corridor, following a route with a few loops around obstacles. Cardboard boxes were arranged as walls and extra obstacles, giving the environment enough geometric features to map.

At each location, the robot ran twice with a different particle count (50 and 100): six test scenarios in total, each producing three maps to compare: a reference map from the robot's own SLAM system, the custom Python implementation's output, and the ROS1 Gmapping benchmark.

Results

Room structure was reconstructed, but sharpness varied a lot

All three approaches recognized each room's overall shape. The difference is in wall sharpness and consistency: ROS1 Gmapping consistently produced crisp, clean walls across every location (SSIM above 0.87 against the reference map), while the custom Python implementation only captured the global structure (SSIM 0.5 to 0.72), with walls that tended to thicken and drift slightly.

An unexpected finding

Adding more particles, from 50 to 100, didn't always make the map more accurate. At the Sisken location, the Python implementation's SSIM score actually dropped to 0.52, suggesting the error wasn't a lack of particles but possibly motion model parameters that were too loose (too much noise), spreading particles too widely even though each one individually still matched the Lidar reading.

Conclusion

Not a hardware problem: the challenge is in the algorithm

The Gmapping framework ran in real time on the Jetson Nano without performance issues. Since ROS1 used the exact same raw sensor data as the Python implementation, its far higher precision proves the Lidar and odometry data itself is reliable. The accuracy gap comes entirely from the custom algorithm's scan matching and resampling strategy, which isn't yet as mature as Gmapping's, not from any hardware limitation.
